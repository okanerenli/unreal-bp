---
name: blueprint-map
description: Read and edit Unreal Blueprint graphs through local Unreal MCP command files. Discover nodes/pins; create events/functions, parameters, primitive/object/container variables, casts, external Get/Set and calls; place macros, bind dispatchers, read connected flows, manage dynamic pins, constants, links, positions, compile and save without screenshots. Also read/edit Material and MaterialFunction expression graphs and MaterialInstanceConstant parameters.
---

Use the bundled Codex-side library rather than manually discovering and calling individual Unreal tools.
Unreal Editor must be open with its existing MCP server at `http://127.0.0.1:8000/mcp`.

From the Unreal project root, run the script using its absolute installed path (resolve `../../scripts/unreal_bp.py` relative to this SKILL.md directory):

```sh
python3 /absolute/plugin/path/scripts/unreal_bp.py map 'StarShipsParentBP'
```

The target accepts an asset name, a unique name substring, a package path or an object path. Ambiguous matches raise an error listing candidates; ask the user to identify the target instead of choosing one. No fuzzy name rewriting.

For a specific function/event/macro, prefer `map TARGET --graph EXACT_GRAPH_NAME`, or select `graph NAME` and use `map graph` in a command file. Plain `map` reads the entire Blueprint even when a graph is selected; use it only when the whole Blueprint is needed. Scoped reads query only that graph and fail on a missing selection/name without falling back to a full map. For a connected chain, prefer `get flow node NODE`.

The command returns one JSON object containing the resolved Blueprint reference and each graph's original node information: node reference, type, position, input/output pins, pin values and connected pin addresses. Pin addresses are the server's node reference + direction + index, not GUIDs. Positions are graph coordinates, not identifiers. Re-read after graph edits; references and pin indices are not a promise of identity across reconstruction.

For a large map, redirect stdout to a task output file and read only the relevant portion. The complete map remains in that file; do not claim a partial excerpt is the entire graph.

For asset metadata and readable property schemas, use `scripts/unreal_bp.py inspect /Game/Path/Asset`; add repeated `--property NAME` flags for specific values. Registry tags and Blueprint class defaults are separate sources. See the command reference for scope and freshness.

For edits, read [the command reference](references/commands.md), write a command file and run:

Default discovery rule: collect the known node-type requirements for the planned flow first, deduplicate by type and declaring class, and request their pin information together with `inspect node_types JSON`. Use the same returned type information throughout planning; do not issue separate single-type inspections for each known node. Use additional focused queries only for newly discovered needs, unresolved ambiguity, or a change that invalidates the earlier information. A single unknown type may still use `inspect node_type`. Batch discovery is one editor tool call after normal session/schema setup, not parallel editor calls or a batch mutation executor. Preview pins are not placed-node addresses: obtain actual node/pin references when wiring, and retain the existing reconstruction/compile verification rules.

```sh
python3 /absolute/plugin/path/scripts/unreal_bp.py syntax
python3 /absolute/plugin/path/scripts/unreal_bp.py run /absolute/path/commands.txt
```

Niagara commands reuse the engine’s registered NiagaraToolsets. See [Niagara commands](references/commands.md#niagara-toolsets) for live tool/schema discovery, native JSON arguments and explicit save. Do not add a duplicate native Niagara bridge. Async compile/issue/fix calls are awaited through the existing MCP transport between managed batches.

The script initializes a fresh MCP session per invocation. `run FILE` sends synchronous commands in a managed `command_batch` call after session/schema/dependency setup; asynchronous Niagara calls split that batch at their original source lines. The editor executes the same shared BP, asset and Material handlers in source order through its existing ToolsetRegistry; it does not issue per-command MCP requests. All runs require the current managed Python dependency. Use one invocation at a time and do not run other editor MCP calls concurrently. Editing requires the user's task to authorize those changes. The CLI emits a batch-start record immediately and emits ordered per-command records after the batch returns. The first error stops execution and returns completed records plus selection/alias state without rolling back edits. A lost connection may lose the response after mutations; inspect live state before resuming. Split work into separate runs wherever returned discovery, referencers, maps or diagnostics must be inspected before deciding the next commands; a read line in a prepared file is not an approval pause. After a failed or interrupted mutation, read the current map and resume only the remaining work; never blindly replay the file. Compile and save are explicit commands. This plugin does not convert C++.

For planned multi-node Blueprint work, follow [Planned Blueprint builds](references/commands.md#planned-blueprint-builds), B1–B8: plan/discover → declare → add → configure → inspect actual pins → connect → verify/compile → save. Use the global batch; end calls at inspection/decision boundaries. Complete dependency functions before callers and prefer `map graph` over full Blueprint reads.

Blueprint comments: use `create comment text TEXT position X,Y size W,H as ALIAS` or `create comment text TEXT nodes A,B padding N as ALIAS`. Read `list comments` or `inspect comment NODE`, then edit with `set comment NODE properties JSON`. Text/visible/pinned apply to ordinary node bubbles too; width/height/color are box-only. Move through existing `position node` and delete through `delete comment`; deleting a box preserves enclosed nodes. Inspection/editing requires native bridge protocol 15. See the command reference for fields and limits.

For one connected event chain, use `get flow node ALIAS_OR_NODE_PATH` instead of fetching each node separately. It returns topology and pin defaults, not runtime execution traces; disconnected nodes and function bodies require separate inspection. Dispatcher declarations and parameters use `create dispatcher` and `add dispatcher_input`; dispatcher nodes reuse `add node`, and Create Event handlers use `list event_functions` / `set event_function`.

Delete signature parameters with `delete function_input`, `delete function_output`, or `delete dispatcher_input name NAME` on the appropriate selected graph. Delete a function with `delete function name NAME`; this clears the selection if it was the active graph.

Required deletion workflow: before deleting a parameter or function, record its owner, signature and known call sites. After deletion, inspect the updated signature and affected call nodes and connections, including known callers in other Blueprints, BEFORE compiling. Compare against the exact deleted member; an unconnected pin alone is not invalid. Explicitly clean only confirmed stale pins, links or calls using supported operations, preserving unrelated connections and upstream/downstream nodes. The library must not silently perform automatic cleanup. If caller coverage or a cleanup operation cannot be verified, report the unresolved scope instead of assuming it is clean. Then compile the affected Blueprints and inspect the results; compilation does not replace the preceding inspection. Do not report deletion work as complete while identified stale references remain unresolved.

For asset creation, select `folder /Game/PATH`, then use `create material`, `create material_function`, `create datatable` or `create bp` as documented in the command reference. `list assets` and `list folders` use this folder recursively. `save` saves only the currently selected/created asset; non-Blueprint creation clears BP graph context. `target` remains Blueprint-only. Use `find row_structs` to discover existing DataTable schemas. New Struct assets use the generic StructureFactory command when the bundled editor-side toolset is installed.

Asset operations: `copy asset SOURCE to DESTINATION`, `move asset SOURCE to DESTINATION`, and `delete asset PATH` use explicit asset paths, not folders. Before deleting, separately read `get referencers asset PATH` / relevant dependencies and inspect the impact; do not batch unread reference output with deletion. Resolve known affected references before deleting and report unresolved scope. Copy/move select the destination for save and clear graph context. Normal copy does not remap dependencies; Advanced Copy is not supported yet.

Generic asset creation uses the bundled Unreal-side `unreal_bp_assets.AssetCreationTools` registered through the existing ToolsetRegistry. See the command reference for installation. Discover with `find asset_types filter TEXT`; `create asset type FACTORY name NAME [options JSON]` uses the selected folder. Read required options from the catalog; discovered does not mean supported. Create dependencies first and use returned paths. Missing dependency references fail before that asset is created, but earlier commands are not rolled back. `refresh asset_types` updates the process-local catalog. Struct asset creation does not edit its members.

For DataTable rows, select `datatable EXACT_PATH` (returns schema), then use `list datatable_rows`, `get datatable_rows JSON_NAME_ARRAY`, `add datatable_rows JSON_NAME_ARRAY`, `set datatable_rows JSON_ROW_PROPERTY_OBJECT`, `rename datatable_rows JSON_OLD_TO_NEW_OBJECT`, or `delete datatable_rows JSON_NAME_ARRAY`. Use exact returned row/schema names; inspect schema before preparing values. Add uses defaults; set only edits existing rows. Read back explicitly and save explicitly. These reuse DataTableTools through the global batch; get/add/set/rename internally process the full table. Before rename/delete, inspect affected row consumers; references are not automatically rewritten. See the command reference for examples and partial-failure behavior.

For Enum asset entries, use `get enum_entries asset PATH`, `add enum_entries asset PATH names JSON_NAME_ARRAY`, `rename enum_entries asset PATH names JSON_ID_TO_DISPLAY_NAME_OBJECT`, and `delete enum_entries asset PATH ids JSON_ID_ARRAY`. Requires native bridge protocol 16. Rename/delete target exact returned internal ids; display-name edits preserve those ids. Commands support multiple entries through the global batch and select the edited enum for explicit save. Before deletion inspect referencers and affected enum consumers, then verify changed uses before compiling/saving them. Native C++ enums are not editable. See the command reference for sequential renames and partial failures.

For struct fields, read `get struct_fields asset PATH`, then use `edit struct PATH fields JSON` as documented in the command reference. Requires native bridge protocol 14. For enum, class, soft object/class and other native pin types, supply `pin_type` with Unreal FEdGraphPinType text returned by field inspection; it is mutually exclusive with the short type/class/struct/container options. Native parsing feeds the same EditStructField validation, without category-specific editing paths. Use `delete struct_field asset PATH name NAME` for deletion and `move struct_field asset PATH name NAME before|after OTHER_NAME` for ordering. `edit struct` supports the existing Blueprint primitive/math, object/struct and container type paths plus optional tooltip. Read referencers and inspect affected consumers before deletion; inspect and resolve exact stale member uses afterward before compiling. The last field cannot be deleted. Use exact returned field names for explicit `rename_from`; unmentioned fields remain intact. Save explicitly. On failure, read the current fields and affected Blueprint graphs before resuming because prior edits remain applied.


Managed editor dependency (required before generic factory operations):
1. Use the user's active local Unreal project directory; do not guess a different project from an asset name. Run the bundled `scripts/unreal_bp.py dependencies --project /absolute/project` command. This uses the existing installer to copy missing/changed module content and preserve startup imports. It requires a working base Unreal MCP connection.
2. Inspect its JSON. Exit code 2 / `ready: false` means installation/loading is incomplete, not success. When `disk_ready` is true, write the exact returned `load_code` to a temporary Python file. If the installed toolset exposes `python_console`, run `scripts/unreal_bp.py console python --file /absolute/load.py`; this also works when that loaded dependency is outdated. Only for first installation or an older version without `python_console`, execute that file in the editor UI console using the available editor tools. Write it to a temporary Python file and execute that file if needed. Use fresh widget refs; never hardcode console coordinates or refs. Focus the console and replace any existing input before typing the load command; a successful Type response alone does not prove execution. Do not create an alternative execution server or restart the editor automatically. If Python/ToolsetRegistry/MCP is unavailable or the loader fails, report the exact blocker.
3. Run `dependencies --project /absolute/project --check` and require `ready: true` before continuing. This verifies the loaded source hash and project/module identity as well as the files on disk. Recheck after a plugin update or switching project/editor; reload only if needed. The user has authorized management of this bundled dependency, so perform routine install/update/load steps yourself rather than sending the user installation chores.
The CLI does not itself drive the editor UI: Codex performs the load step using the returned code. Factory commands also reject a missing, legacy or outdated loaded module. Standalone BP map reads remain usable without the managed dependency; command-file runs require the current shared runtime. Do not describe this as an automatic Codex marketplace dependency installation.

Material editing: select `material EXACT_PATH` and use `map material`, expression commands and `compile material` from [the command reference](references/commands.md#material-graphs-and-instances). These reuse selected_asset and existing MaterialTools/ObjectTools, not Blueprint graph pins. Map includes positions, properties and wiring. Function calls use MaterialExpressionMaterialFunctionCall and its reflected materialFunction property; inspect refreshed pins after assignment. Instance parameters use native protocol 12 identity-aware discovery and typed access with readback; layer/blend parameters retain association and index. Save explicitly. This map is read in one managed editor call after normal setup and seeds the per-run cache; it is not a batch mutation executor. Verify/load the managed editor dependency and native protocol 12 before using material maps, output edits, compile diagnostics or instance parameters.

Material runs maintain a CommandContext cache with mutation invalidation; see the material command reference for boundaries. Reuse discovery within a run. `map material`, `inspect expression`, explicit material selection and parameter listing refresh live data; refresh after manual/external edits. Function property changes invalidate pin information, compile clears the cache, and instance value getters stay live. This is per-run reuse, not persistent state or a batch executor.

For planned multi-node Material/MaterialFunction construction, follow the [Material build method](references/commands.md#planned-multi-node-material-builds) before writing commands. Use `run FILE --batch-material-writes`. Execute the separate Function build steps F1–F8 for each dependency function, then Material build steps M1–M8 for the main material. In BOTH procedures, ALL node additions must finish before ALL property/parameter/function assignments; ALL assignments must finish before the wiring map; read that map before connecting ANY planned nodes. Do not query after each node, property assignment or connection. Use the prescribed phase boundaries and exceptions in that method. Single edits can keep normal immediate readback.

`run` uses the common editor batch by default. `--batch-material-writes` retains the existing Material-specific grouping and deferred readback inside that batch. Keep add/property commands together, use map as the phase boundary, then group connections. Delete/unbind and instance value/override writes are also batched. For staged library calls, retain the same CommandContext with the explicit context argument described in the command reference. Read completed-line results and the failed line on error; never replay the whole batch. Map and compile verification remain explicit. Normal and defer-only modes remain available.
